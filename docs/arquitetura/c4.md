# Documentação C4 — Banco Comunitário

Os três níveis exigidos, em Mermaid, versionados junto com o código. **O `.md` é a fonte**: não há
PNG no repositório, porque imagem exportada envelhece em paralelo ao diagrama. Exporte para
PDF/PNG apenas para submissão.

## 1. Como ler este documento

| Nível | Pergunta que responde | Público | Quando precisa mudar |
|---|---|---|---|
| 1 — Contexto | Com quem o banco comunitário conversa e onde termina a fronteira? | gestão, comunidade, avaliador | entra ator, sistema externo ou integração nova |
| 2 — Contêineres | Quais blocos executáveis/armazenamentos existem e como se comunicam? | equipe técnica | nasce contêiner, muda tecnologia ou protocolo entre blocos |
| 3 — Componentes | Como a API é composta por dentro e quem pode depender de quem? | desenvolvedor | muda fronteira de módulo, camada ou porta |

Convenção de rótulo: **todo relacionamento tem verbo no presente do indicativo** ("solicita",
"grava", "consulta"). Nó marcado `previsto` **não existe no código** — está no desenho porque o
escopo declarado do banco comunitário o exige, e o rótulo deixa isso explícito em vez de fingir
que já foi entregue.

**Notação.** Os três níveis usam `flowchart` do Mermaid com a semântica do C4 — `subgraph` para a
fronteira do sistema, formas e cores por tipo de elemento (pessoa, sistema, contêiner, armazenamento,
externo) e relacionamentos com verbo. O motivo está na §4.4: a notação `C4Context`/`C4Container` do
Mermaid posiciona os nós pela ordem de declaração, e as setas acabavam atravessando caixas
(verificado renderizando). O modelo C4 é independente de notação (Brown); o que precisa ser
consistente é a hierarquia e o vocabulário, não a sintaxe.

Legenda das cores: **azul-claro/stadium** = pessoa · **azul** = fronteira do sistema ou contêiner ·
**âmbar** = armazenamento de dados · **cinza** = sistema externo, previsto
(nos recortes do nível 3: azul-claro = fronteira HTTP, verde = aplicação, verde-claro = domínio,
âmbar = persistência).

## 2. Nível 1 — Diagrama de Contexto

**Escopo:** o Banco Comunitário como uma caixa só. Dentro dela estão a API e o banco de dados;
fora, quem usa e com o que o sistema precisa conversar.

```mermaid
flowchart TB
    MORADOR(["Morador / empreendedor solidário<br/>[Pessoa]<br/>Associado da comunidade"])
    GERENTE(["Gerente de conta<br/>[Pessoa]<br/>Funcionário da associação"])
    CONSELHO(["Conselho gestor<br/>[Pessoa]<br/>Acompanha a prestação de contas"])

    subgraph BANK["Banco Comunitário — fronteira do sistema"]
        SISTEMA["Banco Comunitário<br/>[Sistema de software]<br/>Contas, depósitos, saques, extrato e crédito solidário"]
    end

    EMAIL["Serviço de e-mail<br/>[Sistema externo · previsto]<br/>Notifica operações e crédito"]
    CONVENIOS["API de convênios<br/>[Sistema externo · previsto]<br/>Consulta e paga contas de consumo"]

    MORADOR -->|"Movimenta conta"| SISTEMA
    GERENTE -->|"Consulta contas"| SISTEMA
    CONSELHO -->|"Consulta extrato"| SISTEMA
    SISTEMA -->|"Envia notificação"| EMAIL
    SISTEMA -->|"Paga convênios"| CONVENIOS

    classDef person fill:#1565c0,stroke:#0d47a1,color:#fff
    classDef system fill:#1e88e5,stroke:#1565c0,color:#fff
    classDef external fill:#90a4ae,stroke:#607d8b,color:#fff
    class MORADOR,GERENTE,CONSELHO person
    class SISTEMA system
    class EMAIL,CONVENIOS external```

**Leitura do diagrama**

* A fronteira desenhada é o **Banco Comunitário como um todo**; como não há interface web nem
  aplicativo no repositório, associado, gerente e conselho acessam por cliente HTTP.
* O conselho gestor hoje consome o mesmo endpoint de extrato que o gerente — o diagrama mostra a
  relação, e a seção [§5](#5-o-que-este-diagrama-ainda-não-tem) registra que não existe relatório
  de prestação de contas próprio para ele.
* Os dois sistemas externos estão marcados `previsto`: o escopo do banco comunitário os exige
  (notificar o associado; pagar contas de consumo), o código ainda não os integra. Nenhum deles
  fica acoplado ao núcleo — entram como adaptador quando existirem (ADR-0002, §Extensibilidade).
* Fora do desenho de propósito: serviços de infraestrutura (DNS, TLS, hospedagem). O C4 de
  contexto representa **software**, não topologia de rede.

## 3. Nível 2 — Diagrama de Contêineres

**Escopo:** dentro da fronteira. *Contêiner* no C4 é aplicação ou armazenamento executável/implantável.

```mermaid
flowchart TB
    MORADOR(["Morador / empreendedor<br/>[Pessoa]"])

    subgraph BANK["Banco Comunitário — fronteira do sistema"]
        API["API REST<br/>[Contêiner: Node.js + Express 5 + TypeScript]<br/>Expõe contas, operações e crédito solidário"]
        DB[("Banco de dados<br/>[Contêiner: PostgreSQL 15]<br/>Contas, lançamentos e crédito")]
        MIG["Runner de migrations<br/>[Contêiner: Prisma 8 CLI]<br/>Aplica migrations e verifica o schema"]
    end

    MORADOR -->|"Envia requisição HTTPS/JSON"| API
    API -->|"Lê e grava — SQL"| DB
    MIG -->|"Aplica migrations — SQL"| DB

    classDef person fill:#1565c0,stroke:#0d47a1,color:#fff
    classDef container fill:#1e88e5,stroke:#1565c0,color:#fff
    classDef data fill:#ffb74d,stroke:#ef6c00,color:#000
    class MORADOR person
    class API,MIG container
    class DB data```

| Contêiner | Responsabilidade | Tecnologia | Estado |
|---|---|---|---|
| API REST | Único processo executável do sistema. Recebe HTTP, valida a entrada, executa os casos de uso (`AccountService` em camadas; `CreateSolidarityCreditUseCase` no hexágono) e serializa JSON. | Node.js, Express 5.2, TypeScript 7, `tsx` em dev | existente |
| Banco de dados | Persiste o estado durável: `Account`, `Transaction`, `SolidarityEnterprise`, `CreditRequest`. Guarda as invariantes que só o banco pode garantir (unicidade de documento, `numeric` para dinheiro). | PostgreSQL 15+ | existente |
| Runner de migrations | Aplica `migrations/app/<timestamp>_<nome>` e gera `contract.prisma` → `contract.json`/`contract.d.ts`, que são versionados. Não roda em produção de forma automática (ADR-0003). | Prisma 8 CLI | existente |
| Portal web do cliente | Interface para associado e gerente consumirem a API. | não decidido | **previsto — fora do diagrama** |
| Serviço de notificações | Traduz eventos de operação em e-mail/SMS, fora do caminho da requisição. | não decidido | **previsto — fora do diagrama** |

*Os dois contêineres previstos ficam na tabela, não no desenho: o nível 2 representa o que existe. No
dia em que nascerem, entram no diagrama no mesmo commit (e esta nota sai).*

**Decisões de fronteira que este nível torna visíveis**

* **Um único armazenamento para todos os módulos.** Não há schema separado por módulo (contas ×
  crédito): compartilham a instância e o schema `public`. O isolamento é feito no código, pela
  guarda de dependência — trade-off registrado no ADR-0003.
* **Nada de broker hoje.** Não há fila, broker nem worker no código; a notificação aparece apenas
  como sistema externo *previsto* no nível 1. Introduzir fila é decisão própria (ADR futuro), não
  consequência automática deste desenho.
* **O portal não fala com o banco.** Se ele existir, consome a API — é a razão de a API ser o único
  ponto de escrita.

## 4. Nível 3 — Diagrama de Componentes

**Escopo:** dentro do contêiner **API REST**, que é o candidato natural (concentra todas as regras).

Dois recortes, porque um desenho único com 12 componentes vira ilegível: o renderizador posiciona
os nós automaticamente e os rótulos das arestas caem sobre as caixas. Cada recorte responde uma
pergunta diferente.

### 4.1 Recorte A — caminho de uma requisição no módulo de contas

Pergunta: *"o que acontece entre o `POST /accounts/:id/withdrawals` e o `UPDATE` no PostgreSQL?"*

| Componente | Arquivo | Responsabilidade | Depende de |
|---|---|---|---|
| Rotas / composition root | `src/routes/account.routes.ts`, `src/routes/operation.routes.ts` | Declarar rotas e instanciar repositórios → service → controller. É onde a inversão de dependência acontece de fato. | controllers, services, repositories (classes concretas) |
| Controllers | `src/controllers/AccountController.ts`, `OperationController.ts` | Fronteira HTTP: extrai e valida campos, chama o service, monta a resposta JSON e o código de status. | `AccountService`, `http/validation`, `http/errorHandler` |
| Validação de fronteira | `src/http/validation.ts` | Converte `unknown` do corpo HTTP em tipos confiáveis, com mensagem de erro explícita por campo. | — (só a lib padrão) |
| Serviço de aplicação | `src/services/AccountService.ts` | Orquestra os casos de uso: verifica duplicidade, instancia o domínio, abre a transação do banco, grava conta + lançamento. | domínio, repositórios, `db.transaction` |
| Domínio | `src/models/Account.ts`, `Transaction.ts`, `Money.ts`, `errors.ts` | Invariantes: saldo não nasce negativo, saque não excede saldo, valor estritamente positivo, dinheiro em centavos. Sem framework. | apenas `Money` e erros tipados |
| Repositórios | `src/repositories/AccountRepository.ts`, `TransactionRepository.ts` | Traduzem domínio ↔ linha do banco; aceitam `Client` (global ou transacional); traduzem 23505 em `ConflictError`. | `prisma/db.ts`, `prisma/uniqueConstraint.ts` |
| Client de persistência | `src/prisma/db.ts` | Instancia o client Prisma 8 a partir de `contract.json`; expõe `DbClient`/`TxClient`/`Client`. | PostgreSQL, `DATABASE_URL` |
| Tratamento de erro | `src/http/errorHandler.ts` | Mapeia erro tipado em status por `instanceof`; erro desconhecido vira 500 genérico com o real só no log. | `models/errors.ts` |

**Custo visível neste recorte (e registrado no ADR-0001):** `AccountService` importa `db` e abre a
transação, e as rotas instanciam classes concretas. Ou seja, no módulo de contas a inversão de
dependência é **parcial** — o serviço depende de `AccountRepository` (classe), não de uma porta.

**Seta sólida = chamada; seta pontilhada = implementação ou dependência de tipo.** O núcleo não
aponta para fora: são os adaptadores que apontam para as portas.

| Componente | Arquivo | Responsabilidade |
|---|---|---|
| Composition root | `src/solidarity-credit/adapters/http/solidarity-credit.routes.ts` | Único lugar que conhece as implementações: monta repositório → caso de uso → controller e registra `POST /credit/solidarity` |
| Adaptador primário | `adapters/http/SolidarityCreditController.ts` | Traduz HTTP em `CreateSolidarityCreditCommand`; **tipado pela porta**, não pela classe do caso de uso |
| Porta primária | `application/ports/CreateSolidarityCreditApplication.ts` | Contrato de entrada (`execute(command)`), em linguagem de domínio, sem `Request`/`Response` |
| Caso de uso | `application/useCases/CreateSolidarityCreditUseCase.ts` | Localiza ou cria o empreendimento, constrói `CreditRequest`, delega a persistência atômica |
| Domínio | `domain/CreditRequest.ts`, `domain/SolidarityEnterprise.ts` | Invariantes do crédito (valor positivo, finalidade, vínculo com empreendimento) |
| Porta secundária | `application/ports/CreditRequestRepository.ts` | `findEnterpriseByDocument` + `save(creditRequest, enterprise)` como **unidade de trabalho** |
| Adaptador secundário | `adapters/prisma/CreditRequestRepositoryImpl.ts` | Implementa a porta sobre Prisma 8; a transação (`db.transaction`) mora aqui |
| Guarda de dependência | `scripts/check-hexagon.mjs` (`npm run check:hexagon`) | Falha com exit 1 se `domain/` ou `application/` importarem Express, `@prisma/*`, `src/prisma/`, `src/http/` ou `adapters/` |

### 4.3 Regra de dependência em forma de tabela

O que o desenho afirma, verificável linha a linha:

| De → para | Pode? | Por quê |
|---|---|---|
| `adapters/http` → porta primária | ✅ | Adaptador de entrada depende da abstração do núcleo |
| `adapters/http` → `useCases` | ❌ | O composition root instancia, mas o controller **não** importa a classe do caso de uso |
| `adapters/prisma` → porta secundária e domínio | ✅ | Adaptador de saída traduz entre porta/domínio e banco |
| `application` → `domain` | ✅ | Direção natural do núcleo |
| `application`/`domain` → `express`, `@prisma/*`, `src/prisma/`, `src/http/`, `adapters/` | ❌ | **Verificado por `npm run check:hexagon`** |
| `application`/`domain` → `models/Money`, `models/errors` | ✅ | Núcleo compartilhado do projeto: valor monetário e vocabulário de erro |
| módulo de contas → `solidarity-credit` (ou o inverso) | ❌ hoje | Não há dependência entre os módulos; só compartilham `models/` e `prisma/` |
| domínio → `node:crypto` | ✅ (com nota) | Biblioteca padrão do runtime, não framework. O item opcional de backlog é injetar o gerador de id por porta |

### 4.4 Por que os diagramas usam `flowchart` com semântica C4

A notação nativa do Mermaid para C4 (`C4Context`, `C4Container`, `C4Component`) posiciona os nós
pela **ordem de declaração** e não pela direção dos relacionamentos. Renderizado, o nível 1 saía com
o Banco Comunitário e os dois sistemas externos lado a lado na segunda linha, e a seta "Paga
convênios" atravessava a caixa do serviço de e-mail; rótulos de relações distintas se sobrepunham.
`UpdateRelStyle` com deslocamento resolvia um rótulo por vez e criava outro problema (rótulo longe da
sua seta). A solução adotada foi desenhar os três níveis em `flowchart`, com:

* `subgraph` = fronteira do sistema;
* forma e cor por tipo de elemento — stadium/azul = pessoa, retângulo azul = sistema ou contêiner,
  cilindro âmbar = armazenamento, cinza = externo/previsto;
* rótulo de aresta com verbo (`-->|"Movimenta conta"|`), como pede o enunciado;
* `classDef` no nível 3 para as camadas (fronteira HTTP, aplicação, domínio, persistência).

Isso preserva o que o C4 define — hierarquia de abstração e vocabulário (pessoa, sistema, contêiner,
componente, relacionamento) — e entrega layout previsível. A troca é de **notação**, não de modelo,
e está registrada aqui para quem abrir o arquivo depois saber que foi decisão, não descuido.

O **Nível 4 (código)** não foi produzido: o enunciado não o exige e o `contract.d.ts` gerado pelo
Prisma já documenta o formato exato das estruturas persistidas.

## 5. O que este diagrama ainda não tem

Lista de ausências do **estado atual** — cada linha é também uma dívida: quando o incremento
existir, a linha sai do arquivo no mesmo commit do código.

* **Autenticação e autorização**: todos os endpoints são públicos; não há usuário, sessão, token
  nem perfil. O ator "gerente de conta" no nível 1 não tem identidade no sistema hoje (ADR-0004,
  estado *Proposta*).
* **Interface de usuário**: não há portal web nem aplicativo no repositório; o nível 2 os mostra
  como `previsto`.
* **Integrações externas**: nenhum adaptador de e-mail, SMS, convênios ou pagamento existe no
  código — os dois sistemas externos do nível 1 são `previsto`.
* **Comunicação assíncrona**: não há fila, broker ou worker; a API executa tudo no ciclo da
  requisição.
* **Ciclo de vida do crédito**: só existe a criação da solicitação. Não há análise, aprovação,
  recusa, desembolso, parcelas, limite ou listagem (`status` fica sempre em `"pending"`).
* **Serviços do escopo não implementados**: cartão de crédito popular, pagamento de contas de
  consumo, recebimento de benefícios, gestão de gerentes, prestação de contas diária/semanal.
* **Observabilidade**: sem log estruturado, métrica ou tracing; a única saída é `console.error` no
  middleware de erro.
* **Deploy e CI**: não há pipeline, contêiner de aplicação nem ambiente de homologação; a
  verificação é manual (`npm run typecheck`, `npm test`, `npm run check:hexagon`).
* **Segundo processo**: a API é um único processo; não há *composition root* único do projeto —
  cada arquivo de rota monta a própria cadeia (ADR-0001, consequência negativa).
